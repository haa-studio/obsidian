# 裸寄存器与 HAL 的分工判据（含"配置单一来源"原则）

## 结论

1. 开发规范的本意不是"不许碰寄存器"，而是**不要绕过抽象的语义**。判据只有一条：**这段代码改的是"一次性配置"还是"每拍运行的行为"**。
2. **一次性配置 → HAL / CubeMX**（可读性、可维护性优先，错误由库挡住）；**ISR 内每拍执行 → 裸寄存器**（开销、确定性优先）。
3. 行业惯例也是如此：ST Motor Control SDK、TI InstaSPIN、ODrive 都是**ISR 内裸寄存器、初始化用 HAL/LL**。
4. 真正的不规范不是"用了寄存器"，而是**同一份配置存在两个来源**（`.ioc` 和 User 层的覆盖代码）——配置与代码脱节。
5. 比裸寄存器更危险的是**过时的注释**。

---

## 一、判据

| 类别 | 用什么 | 理由 |
|---|---|---|
| 一次性配置（引脚、时钟、外设模式、DMA 方向） | **HAL / CubeMX** | 可读、可维护、库会挡住常见错误 |
| ISR 内每拍执行 | **裸寄存器** | 50 µs 预算里放不下函数调用；且要确定性、无隐藏状态机 |

**为什么 ISR 里不能用 HAL**：以 `HAL_ADC_Start()` 为例，它会重走一遍 HAL 状态机、可能重配寄存器、还带超时参数。放在 20 kHz 的 ISR 里，开销和不确定性都不可接受。而 `ADC1->CR2 |= SWSTART` 只有一条指令。

## 二、逐项判断（本工程的实际情况）

| 位置 | 频率 | 判断 |
|---|---|---|
| `ADC1->CR2 \|= SWSTART` | 20 kHz | ✅ **必须裸写** |
| `DWT->CYCCNT`（测耗时） | 20 kHz | ✅ HAL 没有这层封装，别无选择 |
| `TIM1->CCR1/2/3` | 20 kHz | ⚠️ 可改可不改。`HAL_TIM_SET_COMPARE` 差异只有几十 ns，用 HAL 也能接受——这一处是"选最直接"而非"选最规范" |
| ADC 序列配置（SQR/SMPR） | 上电一次 | ❌ 应归 CubeMX，见第三节 |
| 整个 SPI2（16bit 帧收发） | 上电十几帧 | ❌ 明确的技术债，无任何性能理由 |
| `TIM1->BDTR`（死区） | 上电一次 | ⚠️ 妥协：`tim.c` 归 CubeMX，重生成会写回旧值 |

## 三、真正的问题：配置有两个来源

### 3.1 症状

User 层代码覆盖了 `.ioc` 的配置，但 `.ioc` 没同步改。于是：

- 打开 CubeMX 看到的配置 **和实际运行的不是一回事**
- 想改参数时，改 CubeMX 不生效、改代码又不知道改哪
- 排查问题时，两个地方都要看

### 3.2 一个真实的代价

曾为测 VDDA 临时"借用"ADC 做一次单通道转换，代码里写了 `ADC1->CR1 = 0`。

`CR1` 的 `SCAN` 位被清掉后，**F4 的 ADC 会忽略序列长度、只反复转换第一个 rank** ⇒ DMA 搬回来的 4 个值全是 PA0。

表现出的假象：

| 现象 | 真相 |
|---|---|
| 四通道读数永远几乎相等 | 就是同一个脚 |
| 三相"同增、扣共模后 0" | 同一个脚，当然没有差模 |
| VBUS 与电流读数相同 | 同一个脚 |
| 零点跨上电乱跳几百码 | 同一个脚在不同时刻的噪声 |

因为"配置分散在两个地方"（`Adc_MeasureVrefInt` 和 `Adc_FocStart` 各写一部分），改一处漏一处的可能性大增。这个假象骗了三天。

### 3.3 正确做法：借完还回去

```c
/* 借用前存档 */
uint32_t sv_cr1 = ADC1->CR1, sv_sqr1 = ADC1->SQR1, sv_sqr2 = ADC1->SQR2;
uint32_t sv_sqr3 = ADC1->SQR3, sv_smpr1 = ADC1->SMPR1, sv_smpr2 = ADC1->SMPR2;

/* 临时改成单通道…… */

/* 用完原样恢复 */
ADC1->CR1 = sv_cr1;  ...
```

而不是让调用方事后补救（"我在启动函数里再置一次 SCAN"）——**后者是打补丁，前者是根治**。

## 四、过时注释比没有注释更危险

曾有一句注释写着"CubeMX 生成的 adc.c 有三处不符合要求：`NbrOfConversion = 1`、`SamplingTime = 3 cycles`……"

实际情况是：**`.ioc` 和 `adc.c` 早就被改对了**（4 rank、CH0~CH3、15/15/15/28），只有注释停留在早期状态。结果基于这句注释做出了错误判断，还差点让人去改一个本来就正确的 `.ioc`。

> [!warning] 判据
> **不要相信注释，要核对生成代码。** 注释描述的是"当时为什么这么写"，代码才是"现在是什么"。

被删掉的那段覆盖代码（`SQR1/SQR3/SMPR2` 手写）就是纯冗余——它一直在重复 HAL 已经做好的事，还让"配置源"看起来有两个。

## 五、两条可操作的规则

1. **`.ioc` 是配置的唯一真相。** 想在 User 层覆盖前，先问：能不能直接在 CubeMX 里配对？如果能，就配在那。
2. **任何"临时借用外设"的代码，必须显式恢复它改过的每一个寄存器位。** 借的范围越窄越好（只碰必要的位），恢复要放在同一条路径上，不要依赖调用方。
